SEGUIMIENTO DE APERTURAS

Instalacion nueva:
- DBs\opendoors.sql ya incluye solicitudes_apertura, ambos contadores y
  los triggers de auditoria compatibles. No ejecutar las migraciones de
  seguimiento sobre ese esquema nuevo.
- Instalar DBs\empresas.sql, DBs\opendoors.sql y DBs\gestalo.sql en ese orden.
  Los triggers usan los nombres empresas, opendoors_v2 y gestalo en el mismo
  servidor; crear gestalo antes de importar su archivo y no insertar empresas
  hasta instalar los tres. Revisar versiones y permisos indicados en los SQL.
- empresas_modulos.licenciaExpira controla el panel hasta el final de la
  fecha guardada, usando la zona SQL de empresas (-05:00). Las API de
  dispositivos y enlaces publicos permanecen operativos al vencer.

Para una base instalada con la version de DBs\opendoors.sql que tenia
cantidadAperturas y no tenia solicitudes_apertura, usar
opendoors_seguimiento_nuevo.sql una sola vez, con respaldo y mantenimiento.
Conserva el contador anterior en cantidadAperturasExitosas e inicializa
fallidas en cero. El contador historico podia incluir cancelaciones y no
permite recuperar la distincion real entre exitos y fallos. El DDL no es
atomico; detenerse y revisar el estado si ocurre un error. No ejecutar esa
migracion en instalaciones ya migradas.

El procedimiento siguiente corresponde exclusivamente a una instalacion
anterior que ya tiene los dos contadores, pero aun no tiene solicitudes:
Antes del despliegue:
- Respaldar opendoors y detener temporalmente las ordenes de apertura.
- Renombrar cantidadAperturas a cantidadAperturasExitosas, conservando valores.
- Agregar cantidadAperturasFallidas INT NOT NULL DEFAULT 0.
- La migracion normaliza contadores NULL a cero y fija INT NOT NULL DEFAULT 0.
- Ejecutar seguimiento_aperturas.sql sobre opendoors. Elimina el antiguo
  trigger de conteo y agrega solicitudes persistentes con vencimiento UTC.
- El usuario PHP necesita SELECT, INSERT, UPDATE y DELETE en solicitudes_apertura,
  ademas de sus permisos existentes sobre locales y microcontroladores.

El sistema suma un exito y actualiza ultimaApertura en UTC al confirmar
la orden. Suma un fallo y restablece accionar=0 si no se confirma en 30 segundos.
Actualiza todos los dispositivos del local y empresa. Anular manualmente no
modifica contadores ni ultimaApertura. Los reintentos no duplican resultados.
No se emite una segunda orden mientras la anterior siga pendiente.
Cada pantalla consulta su propia solicitud: un fallo o anulacion no se
presenta como exito solo porque accionar haya vuelto a cero.
La primera consulta de la pantalla que obtiene el resultado final elimina
la solicitud. Las pendientes no se eliminan y los contadores no se modifican.
Una vez eliminada, ya no se puede volver a consultar el resultado individual.
Si nadie consulta el resultado, la solicitud finalizada permanece en la BD.
Si la respuesta se pierde tras eliminarla, no se puede recuperar el resultado.

PROCESO OBLIGATORIO DE VENCIMIENTO

Docker inicia el proceso automaticamente junto con Apache. Si cualquiera
de los dos termina inesperadamente, el contenedor termina con error para
que la politica de reinicio del despliegue pueda reiniciarlo.

Fuera de Docker (incluido XAMPP), ejecutar permanentemente, con las mismas
variables DB_* del servidor web:

php Modulos\OpenDoors\Nucleo\util\procesar_aperturas.php

Configurar su inicio automatico y reinicio ante errores en el gestor de
servicios del servidor. Comprueba los vencimientos cada segundo incluso
sin navegadores abiertos. Tras una interrupcion recupera las solicitudes
pendientes al arrancar. Las API tambien revisan el plazo antes de confirmar.
Sin este proceso no se garantiza el registro puntual si no llegan peticiones.

Para una ejecucion puntual o un planificador externo:
php Modulos\OpenDoors\Nucleo\util\procesar_aperturas.php --una-vez

Una programacion cada minuto no garantiza el limite de 30 segundos.
El proceso no debe publicarse por HTTP. Su directorio util esta bloqueado.

  prueba concurrencia, rollback y un vencimiento real de 30 segundos sin HTTP.

  Importa DBs\empresas.sql y DBs\opendoors.sql en bases temporales aisladas.
  Simula solo la tabla gestalo.empresas requerida por el trigger: no valida el
  esquema completo ni la compatibilidad de DBs\gestalo.sql con MariaDB.
